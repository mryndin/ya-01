1. Описание функциональности монолитного приложения
Управление отоплением (Устройствами):

Пользователи могут добавлять новые датчики и устройства в систему (CRUD операции: создание, чтение, обновление, удаление).

Пользователи могут обновлять целевые показатели датчиков (например, устанавливать значение, включать/выключать статус), что имитирует управление отоплением.

Реализован базовый поиск датчиков по ID и получение списка всех устройств.

Мониторинг температуры (Телеметрия):

Система запрашивает данные о температуре из внешней системы (Temperature Sensors API) по HTTP.

Пользователи могут просматривать текущую температуру в привязке к локации (например, "Kitchen", "Living Room").

Получение данных происходит в реальном времени по запросу пользователя (Pull-модель).

2. Анализ архитектуры монолитного приложения
Язык программирования: Go (Golang) 1.22. Используется веб-фреймворк Gin для реализации REST API.

База данных: PostgreSQL. Используется драйвер pgx. Схема данных простая: одна таблица sensors для хранения метаданных и состояний устройств.

Взаимодействие:

Синхронное (Blocking I/O): Взаимодействие между модулями жесткое. При запросе списка датчиков (GetSensors) сервер делает блокирующий HTTP-вызов к внешнему сервису температуры.

Отсутствие асинхронности: Нет очередей сообщений или фоновых воркеров.

Безопасность: Полностью отсутствует. Нет middleware для аутентификации (JWT/Session), API открыто для любого клиента сети.

Развертывание: Контейнеризация через Docker (Multi-stage build). Приложение поставляется единым бинарным файлом. Для обновления любого компонента требуется перезапуск всего сервиса.

3. Определение доменов и границы контекстов
Исходя из анализа кода и бизнес-целей, в текущем монолите можно выделить следующие логические области (которые в будущем станут кандидатами на микросервисы):

Context: Device Management (Управление устройствами)

Ответственность: Учет оборудования, хранение метаданных (имя, тип, локация), CRUD операции над сущностью Sensor.

Сущности: Датчик (Sensor), Реле.

Context: Telemetry (Телеметрия и Мониторинг)

Ответственность: Получение "сырых" данных от внешних систем, агрегация показателей температуры, предоставление данных пользователю.

Сущности: Показание температуры (TemperatureReading).

Context: User Access (Пользователи и Доступ) — Отсутствует, но необходим

Ответственность: Идентификация пользователя, разграничение прав доступа к домам/устройствам. В текущем коде ("As-Is") этот домен не реализован, что является архитектурным долгом.

4. Проблемы монолитного решения
Высокая связность (High Coupling) и Отказоустойчивость:

Модуль обработки запросов пользователей напрямую зависит от внешнего Temperature API. Если внешний сервис датчиков ("Temperature API") начнет отвечать медленно или упадет, пользовательский интерфейс зависнет или выдаст ошибку 500. Принцип Cascade Failure.

Отсутствие безопасности:

В коде (routes) нет проверки токенов. Любой человек, знающий IP-адрес, может управлять отоплением в чужих домах. Это блокирует выход на рынок SaaS.

Проблемы масштабируемости (Scalability):

Нельзя масштабировать только функцию "сбора телеметрии" (которая будет расти лавинообразно с подключением новых домов) отдельно от функции "админки устройств". Придется множить весь монолит, потребляя лишнюю память.

Сложность разработки (Time-to-Market):

Все команды (QA, Dev, Support) работают с одним артефактом. Любое изменение требует полного регрессионного тестирования всего приложения.

5. Визуализация контекста системы — диаграмма С4
Диаграмма отражает текущее состояние (As-Is) с акцентом на синхронную природу и отсутствие безопасности.
