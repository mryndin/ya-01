# 🏠 Проект: Гибридная микросервисная архитектура "Умный Дом"

Этот документ содержит описание процесса трансформации монолитного приложения в микросервисную архитектуру в рамках проекта **ya-01**.

---

## Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения
Текущая система (Legacy Monolith) управляет отоплением и мониторингом температуры:
* **Управление отоплением:** Пользователи могут включать/выключать систему, задавать целевую температуру. Система поддерживает автоматическое поддержание режима.
* **Мониторинг температуры:** Система считывает данные с физических датчиков, хранит историю изменений и предоставляет API для получения текущих значений.

### 2. Анализ архитектуры монолитного приложения
* **Стек:** Приложение написано на языке **Go**.
* **База данных:** PostgreSQL (схема `public`).
* **Взаимодействие:** Все компоненты (логика датчиков, API, работа с БД) находятся внутри одного исполняемого файла.
* **Проблема:** Логика безопасности (кто владеет домом) и логика обработки телеметрии жестко связаны с кодом управления оборудованием.

### 3. Определение доменов и границы контекстов
В рамках проектирования выделены следующие контексты:
1.  **Identity (Security) Context:** Регистрация пользователей, домов и управление правами доступа (ACL).
2.  **Telemetry Context:** Прием данных от устройств (IoT), валидация и первичная обработка.
3.  **Core Monolith Context:** Управление физическими характеристиками датчиков и историей температур.

### 4. Проблемы монолитного решения
* **Масштабируемость:** Невозможно отдельно масштабировать прием телеметрии (высокая нагрузка) и API управления.
* **Безопасность:** Отсутствует централизованная проверка прав доступа (любой может послать данные на любой датчик).
* **Сложность:** Внесение изменений в логику авторизации требует пересборки всего сервиса управления домом.

## Задание 4. Создание и документирование API

Для взаимодействия микросервисов используется гибридный подход:
1.  **REST API (Synchronous):** Для управления пользователями, домами и настройки прав (Identity Service).
    * [Спецификация OpenAPI](schemas/to-be/API/openapi-identity-service.yaml)
2.  **MQTT + AsyncAPI (Asynchronous):** Для передачи телеметрии от датчиков.
    * [Спецификация AsyncAPI](schemas/to-be/API/asyncapi-telemetry.yaml)

## Задание 5-6. Разработка и запуск MVP

### Описание решения
В папке `apps/` реализован рабочий прототип (MVP):
* **Identity Service (Java/Spring Boot):** Управляет владельцами и правами.
* **Telemetry Service (Python):** Слушает MQTT, проверяет права и обновляет Монолит.
* **Temperature API (PHP):** Генератор случайных значений.
* **Legacy Monolith (Go):** Хранилище состояния датчиков.

**Визуализация процесса (Workflow):**
![Workflow](schemas/to-be/workflow.png)

### 🚀 Инструкция по развертыванию

Все команды выполняются из директории `apps/`:

1.  **Полная сборка и запуск инфраструктуры:**
    ```bash
    cd apps
    init.bat
    ```

2.  **Запуск сценария тестирования (Workflow):**
    ```bash
    demo_workflow.bat
    ```

**Технологический стек MVP:** Java 17, Python 3.10, PHP 8, Go, MQTT (Mosquitto), PostgreSQL 15, Docker.
